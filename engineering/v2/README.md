# Helium companion — revision 2 engineering dossier

**Decision:** Prototype a nominal 62 cm helium envelope, a protected 2,000 mAh battery and a direct-1S power system. Keep propulsion, camera and audio on a supervised test rig until receiving tests pass. No heater dependency, no fleet purchase, and no claim of validated autonomous flight.

**Status:** Calculations, deterministic parameter sweeps and software tests have run. No balloon has been manufactured or weighed, no motor has been bench-tested here, and no hardware has been purchased. This revision supersedes the v1 component recommendation and its unqualified 32 g envelope allowance, not the fact that v1 firmware is uncompiled.

## Reproduce

Python 3.10 or newer; no third-party dependencies for the simulations/tests:

```bash
python -m unittest discover -s tests -v
python engineering/model.py
```

The second command regenerates CSV sweeps and `reports/results.json`. The xlsx is a separate formula-driven decision model; recorded simulation outputs in the report are regenerated by Python, not by changing an xlsx input.

The previous package's 27 tests were rerun and passed. This revision adds 36 model/interface tests, all passed. The tests validate arithmetic, unit conversion, parameter bounds, a numerical braking integrator against a closed form, and declared interface checks. They do **not** validate the underlying assumptions or physical performance.

## Not implemented or verified

Physical envelope shape; weld/valve strength; helium permeability; wet/conditioned film mass; current-limited guarded thrust (especially reverse); actual OV5640/OV3660 power; useful speaker loudness; radio link near metallized film; flight controller integration; thermal/electrical protection verification; localization; obstacle avoidance; autonomous dock; lifting/grasping.

The original ESP32 Arduino firmware was not cross-compiled in this environment: the Arduino CLI/toolchain is absent, and fetching the CLI failed because the host could not resolve downloads.arduino.cc. A native Python test is not a substitute for compiling/flashing the embedded target.

No physical test rows are populated in the acceptance log. No orders or supplier messages were sent.
